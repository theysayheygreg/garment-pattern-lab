# V0.1 Dirty End-To-End Spike Plan

Date: 2026-05-03

This is the next build move.

Status: first dirty package generated. Run `npm run v0.1:generate` from the repo root to regenerate outputs, and `npm run check` to verify readiness without writing files.

The point is not clean architecture. The point is to force one verifiable garment through the whole pipeline so the project can learn where the abstractions need to be.

## Target

**One sleeveless A-line woven dress/tunic generated from one measurement set into one human-readable package with one static preview and one human sanity check.**

```text
one garment
one measurement set
one ugly generator
one SVG package
one static preview
one validation/readiness report
one human sanity check
```

## Non-Goals

- No broad canvas.
- No automated sketch parsing.
- No full natural-language assistant.
- No production pattern guarantee.
- No marker optimization.
- No grading.
- No real cloth simulation.
- No industrial DXF/AAMA/ASTM export.
- No PDM/PLM/collaboration.
- No full geometry-kernel abstraction before the generator proves what it needs.

## Working Folders

Reusable code can start ugly, but should still land in the correct ownership zones:

```text
packages/pattern-core/
packages/validation-core/
packages/export-core/
packages/preview-3d/
garments/a-line-dress-tunic/
  docs/
  fixtures/
    measurements/
    parameters/
    patterns/
    validation/
  outputs/
```

Use `garments/a-line-dress-tunic/` for garment-specific drafting formulas, measurement fixtures, generated pattern fixtures, and output packages.

Use `packages/` only for logic that should survive the second garment.

### 4. One PatternGraph Candidate

Path:

`garments/a-line-dress-tunic/fixtures/patterns/v0.1-candidate.pattern.json`

Status: generated.

Important schema choices to make explicitly:

- `BodyMeasurementSet` and `PatternMeasurements` are separate.
- seam lines and cut lines are separate.
- darts are first-class enough to validate, even if v0.1 starts dartless.
- notches attach to seam/edge intent.
- foldline is semantic, not just a decorative line.
- assumptions are recorded as provenance.

### 5. One Internal Readiness Report

Path:

`garments/a-line-dress-tunic/fixtures/validation/v0.1-readiness.json`

Status: generated.

This is backend instrumentation, not the fashion designer's error console.

Minimum checks:

- units are millimeters
- panels are closed
- seam lines and cut lines exist
- side seam lengths are within tolerance
- shoulder seam lengths are within tolerance
- grainlines exist
- labels and cut counts exist
- seam allowance exists
- known limitations are listed

State model:

- `blocker`
- `normalization`
- `designer_choice`
- `assumption`
- `limitation`
- `ready`

Designer-facing summaries should use interpretation/readiness language, not error/warning/repair language.

### 8. One Human Sanity Check

Path:

`docs/research/v0.1-human-sanity-check.md`

Status: scaffolded, not reviewed yet.

Questions:

- Is this garment-family recognizable?
- Are the pieces understandable?
- Is the cut package legible?
- Are any assumptions obviously wrong?
- Would this be worth refining toward a muslin?
- What is the first patternmaking correction a human would make?

This checkpoint can be Kiko, a sewing-literate reviewer, or a future patternmaking consultant. It should happen early, before polishing the app.

## Build Order

1. Create measurement and parameter fixtures.
2. Hand-sketch the simplest JSON shape for the candidate.
3. Write the ugly generator.
4. Write the internal readiness checks.
5. Export SVG and markdown package.
6. Add static preview.
7. Run local smoke checks.
8. Capture human sanity check.
9. Then extract reusable pieces into cleaner packages.

## Acceptance Criteria

V0.1 is complete when:

- `npm` or equivalent local command produces the output package.
- The SVG opens in a browser.
- The package includes JSON, SVG, cut sheet, assembly notes, readiness notes, and preview.
- The readiness report records known limitations instead of hiding them.
- A human has looked at the package and recorded whether it is insane, promising, or unclear.

## Implementation Bias

Be crude but honest.

- Prefer a working generator over a perfect schema.
- Prefer clear output over broad functionality.
- Prefer one real path over many speculative abstractions.
- Prefer backend readiness instrumentation over user-facing diagnostic noise.
- Extract architecture only after the garment has gone through the path once.
