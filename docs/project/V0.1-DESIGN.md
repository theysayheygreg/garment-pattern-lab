# Garment Pattern Lab v0.1 — Design Spec

Date: 2026-05-03
Status: Proposed; Codex-ready for implementation
Supersedes: B0–B10 sequencing in `PROTOTYPE-BUILD-ORDER.md` for the v0.1 scope only

This document is the canonical specification for v0.1. It is the answer to: *what does Greg show Kiko at dinner?* It commits to a one-shot, headless-pipeline-with-a-thin-UI prototype that produces a sewable pattern from one input on one garment family. The scope is deliberately narrow.

## North Star

**Kiko gives Greg an image, sketch, or vector file. The pipeline produces a printed PDF pattern Kiko could plausibly print at home, cut, and sew into a muslin.** A simple Three.js viewer with turn/pan shows the panels assembled on a body proxy. An export button on the viewer produces the package.

That is v0.1's product proof. Everything else is deferred.

## Personas and Version

- **Primary persona (v0.1):** Persona 1 — Individual Fashion Designer (`docs/design/personas/persona-1-individual-designer.md`). Kiko-shape user.
- **Operator (v0.1):** Greg, working as developer-on-Kiko's-behalf. Greg drives the pipeline; Kiko sees only the printed pattern and the 3D viewer.
- **Deferred personas:** Persona 2 (Production-Focused Designer, v0.5+) and Persona 3 (Manufacturing-Focused Designer, v1+). Their features are out of scope.

## In Scope

- One garment family: **sleeveless A-line woven tunic / dress** (locked, per the existing decision log).
- Input formats: clean technical flats, vector files (`.svg`, vector PDF), Procreate/Illustrator-shape vector exports, croquis-with-figure raster sketches.
- Vectorization for raster inputs via Potrace + VTracer behind a recipe-driven bridge.
- Semantic interpretation via heuristic priors from `docs/data-corpus/garment-family-landmark-priors.json` for the A-line tunic.
- Scale calibration: imperial units throughout; scale derived from a human figure or croquis in the input image.
- Drafting via existing formulas in `docs/data-corpus/drafting-formulas-a-line-tunic.json` (FreeSewing Bella factors + Aldrich ease + SewGuide flare math).
- Validation via the existing `validation-core` readiness checks (engine instrumentation, not user-facing).
- Marker layout: simple non-optimized strip pack on a 45" fabric width; reports total fabric length consumed.
- Output package: tiled PDF (imperial, letter / A4 home printer pages with alignment marks) containing pattern panels, cut sheet, assembly notes, marker layout. Plus the source `PatternGraph` JSON for the dev surface.
- Three.js viewer: single page, turn/pan controls, panels rendered in static assembly placement around a body proxy, export button.
- Dev instrumentation: `readiness.json` + a debug overlay showing labeled vs unlabeled curves with confidence scores.

## Out Of Scope

Explicitly deferred from v0.1:

- **Editing of any kind.** No assistant verbs, no parameter sliders, no in-product correction. v0.1 is one-shot. (Editing lands in v0.5 with the assistant verb set.)
- **Garment families other than A-line tunic.** The corpus catalogs 22 families; v0.1 binds to one.
- **Drape photos and noisy raster inputs.** v0.1 expects clean inputs. Drape photos and phone-photographed sketchbook pages are v0.5 concerns.
- **Manual landmark correction surface.** When interpretation is low-confidence the system best-guesses and surfaces assumptions in the output package; the developer iterates from dev instrumentation. No drag-to-fix UI.
- **Variants, grading, dependency propagation, multi-pattern workspace.** All Persona 2 features (v0.5+).
- **Industrial export (DXF / AAMA / ASTM), marker optimization, multilingual factory instructions, approval gates.** All Persona 3 features (v1+).
- **Cloth simulation / drape preview.** The 3D view is *static panel placement*, not cloth physics. (See `KEW-PRODUCT-VISION.md` and Q on drape terminology.)
- **Knit fabric handling.** v0.1 assumes woven fabric.
- **Closures beyond pullover.** Center-back zipper, buttons, ties — all deferred.
- **Scale-calibration UI.** If the input lacks a human figure, the system falls back to a canonical body or refuses; there is no interactive scale-set tool.

## Pipeline Overview

```
input file (.svg | .ai | vector PDF | clean raster)
  -> ingest
  -> vectorize (raster path) or passthrough (vector path)
  -> semantic interpretation (heuristic priors for A-line tunic)
  -> scale calibration (figure-driven, imperial)
  -> draft pattern (FreeSewing/Bella formulas)
  -> validate
  -> static panel layout
  -> marker layout (45" fabric, non-optimized)
  -> export package
     -> tiled PDF (pattern + cut sheet + assembly + marker)
     -> PatternGraph JSON (dev artifact)
     -> Three.js scene data
  -> Three.js viewer page (turn/pan + export button)

dev surface (parallel to pipeline):
  -> readiness.json
  -> labeled-curves debug overlay
  -> dev-artifacts/ directory
```

Each stage runs once per input. There is no looping, no editing, no re-interpretation after promotion.

## Stage-By-Stage Contract

### Stage 1 — Ingest

**Inputs accepted:** `.svg`, vector PDF, `.ai` (best effort; if proprietary blocks, document and accept passthrough failure with a clear dev message), clean raster (`.png`, `.jpg`, `.webp`, single-page PDF raster).

**Behavior:**
- Vector inputs (.svg, vector PDF, .ai) → passthrough or best-effort SVG conversion to Stage 2 with a `vector` recipe tag.
- Raster inputs → Stage 2 with a recipe tag chosen by image characteristics (heuristic: white background + black lines → `clean-technical-flat`; otherwise → `pencil-sketch`).

**Output:** normalized internal representation with provenance fields (file path, format, recipe tag, hash for reproducibility).

**Failure:** if the file cannot be read at all, fail loudly with a clear dev message in `readiness.json`.

**Done when:** every accepted format produces a passthrough payload that Stage 2 can consume; failure cases produce useful dev output.

### Stage 2 — Vectorization

**Engine:** first runnable implementation uses `@neplex/vectorizer`, a MIT VTracer-backed Node package with direct Buffer input, for clean raster smoke tests and color/segmented inputs. Potrace remains a research comparison for black-line flats and scanned sketches, but its GPLv2 license keeps it out of the default prototype dependency path. Recipe-driven, per `docs/research/vectorization-for-garment-ingestion-2026-05-03.md`.

**Behavior:**
- Vector passthrough → no work; pass through with provenance.
- Raster + recipe tag → run the appropriate tracer with the recipe's parameters.
- Post-trace: deterministic layer separation (silhouette / interior / annotation) by simple heuristics (closed paths bordering image edge = silhouette; closed paths inside silhouette = interior features; short open paths = annotations).

**Output:** structured vector data — list of paths each with role tag (`silhouette` | `interior` | `annotation` | `unclassified`), bounding box, and provenance (source recipe + tracer + version).

**Failure:** if the tracer crashes or returns empty output, surface a clear dev message and stop the pipeline.

**Done when:** v0.1 reference inputs from Kiko produce structured vector data with stable layer assignments.

### Stage 3 — Semantic Interpretation

**Engine:** heuristic interpreter loading `docs/data-corpus/garment-family-landmark-priors.json` for the `sleeveless-a-line-woven-tunic` family. Per `docs/research/semantic-curve-interpretation-soa-2026-05-03.md`.

**Behavior:**
- For each landmark slot in the prior (hem_front, hem_back, neckline_front, neckline_back, shoulder_left/right, armhole_left/right, side_seam_left/right, center_front, center_back, optional bust_dart_left/right, optional waist_dart_back_left/right): apply the weighted heuristic rules to candidate curves, score each candidate, pick the best.
- For each pick, record confidence (`[0, 1]`) based on combined rule scores.
- Below each slot's `ambiguity_threshold`: best-guess proceeds, but the assignment is flagged as `assumed` with reason text in design language.
- Required slots that fail to fill (no candidate above 0.3 floor) → pipeline refuses with dev message.

**Output:** `SketchIntent` (semantic labels) + `LandmarkSet` (geometric points) + `AmbiguityReport` (per-slot confidence + assumption notes for assumed picks).

**Note on landmark prior implementability gaps:** the prior file's `known_implementability_gaps` register lists five concrete gaps (mirror rules referenced by id without bodies, prose rule strings rather than DSL, undocumented labeling-order dependencies, unit-bearing priors on unitless input, missing axis-absent fallback). Codex must close these gaps as part of Stage 3's implementation. Specifically:

- Implement rule ids as keys into a TypeScript function table (the strings are documentation).
- Define mirror rules programmatically via reflection across the vertical center axis.
- Define an explicit `labeling_order` array per family.
- Apply scale-proof (Stage 4) before any unit-bearing rule.
- Add `requires_axis` boolean per heuristic with axis-absent fallback weighting.

**Done when:** the existing v0.1 reference fixtures plus 1–2 of Kiko's reference inputs produce stable, plausible landmark assignments with confidence scores.

### Stage 4 — Scale Calibration

**Engine:** new module `packages/sketch-intent/src/scale-calibration/`.

**Behavior:**
- Detect a human figure or croquis in the input (heuristic: vertical span, pose stance, or matching a known croquis template by SSIM).
- If found: measure pixels-per-inch from anatomical landmark spacing — chest-to-waist, waist-to-hip, hip-to-knee, knee-to-ankle. Use a canonical body table (default: 5'5" / 165cm female with standard segment ratios) to derive inches-per-pixel.
- If not found: fall back to a canonical default scale (assume the garment is drawn at a fixed pixel-per-inch ratio, configurable in dev).
- Record scale evidence in `UnitProfile` with confidence.

**Output:** scale factor (inches per pixel) + confidence + evidence source (figure-detected | default-fallback).

**Failure:** never fails; always returns a scale even if low-confidence. Low-confidence scales surface as a warning in the package.

**Done when:** v0.1 reference inputs that include a figure produce calibrated scale within ±10%; figure-less inputs use the default and surface a warning.

### Stage 5 — Draft Pattern

**Engine:** existing drafting logic from `packages/pattern-core/` driven by `docs/data-corpus/drafting-formulas-a-line-tunic.json`.

**Behavior:**
- Convert calibrated landmarks + measurements to garment parameters (neckline depth, shoulder width, armhole depth, ease values, length, hem sweep). Where the landmarks contradict the measurement set, the assistant collaborator surfaces the conflict for Greg to resolve manually (no UI; fix the input).
- Run the FreeSewing/Bella + Aldrich + SewGuide drafting math.
- Produce front and back panels with seam lines, cut lines, grainlines, fold lines, notches, and labels.

**Output:** `PatternGraphCandidate` per the graph topology committed in the decision log (panels as first-class typed nodes, edges with semantic role, etc.). Imperial units throughout.

**Failure:** if the drafting math produces a non-closed panel or impossible geometry, fail with dev message.

**Done when:** v0.1 reference inputs produce closed front and back panels that pass the existing validators.

### Stage 6 — Validation Gate

**Engine:** existing `packages/validation-core/`.

**Behavior:**
- Run the existing readiness checks (units, panel closure, grainline, label, seam-pair length, known-limits).
- Promote `PatternGraphCandidate` to `PatternGraph` only if no hard errors.
- Soft errors and assumptions proceed to export with notes in the package.

**Threshold for v0.1:** "good enough to muslin" — Persona 1's bar. Permissive on warnings and assumptions; strict on geometry impossibility.

**Output:** promoted `PatternGraph` or refusal with dev message.

**Done when:** the existing validators run cleanly against the v0.1 pipeline output for known-good and known-bad fixtures.

### Stage 7 — Marker Layout

**Engine:** new module `packages/export-core/src/marker-layout/`.

**Behavior:**
- Lay out the front and back panels (with seam allowances) on a 45" wide strip in a simple non-optimized arrangement: panels placed sequentially along the strip with a fixed spacing (1" gutter), grainlines aligned vertically.
- Compute total fabric length consumed.
- Produce a marker-layout SVG page sized to 45" × computed-length.
- No rotation, no mirroring, no nesting optimization. v1+ work.
- [started 2026-05-04] Current implementation writes `package/marker.svg` and `dev-artifacts/marker-plan.json` with 45 inch width, sequential placement, and fabric-length metrics. Marker PDF is still deferred to export packaging.

**Output:** marker-layout SVG + `MarkerPlan` JSON with consumption metrics.

**Done when:** the front+back panels lay out on 45" with a clear consumption number and a printable marker-layout page.

### Stage 8 — Export Package

**Engine:** existing `packages/export-core/` extended with PDF tiling.

**Behavior:**
- Compose the user-facing PDF: cover page (garment name, size, fabric width, total fabric length), pattern panel pages (tiled to letter / A4 with alignment marks), cut sheet, assembly notes, marker layout.
- Use PDFKit or pdf-lib for tiled PDF generation.
- Imperial units throughout; every dimension labeled in inches.
- Include an "Assumptions" section listing what the system guessed from low-confidence interpretation.
- Bundle the user package into `garments/a-line-dress-tunic/outputs/v0.1-demo/package/`.
- Bundle dev artifacts (`readiness.json`, debug overlay, `PatternGraph` JSON, raw vectorized geometry, scale-calibration trace) into `garments/a-line-dress-tunic/outputs/v0.1-demo/dev-artifacts/`.
- [started 2026-05-04] Current implementation writes `package/manifest.json` as the package inventory/provenance surface. Tiled PDF remains deferred.

**Output:** `package/` and `dev-artifacts/` directories per input.

**Done when:** the package directory contains a printable PDF, cut sheet, assembly notes, and marker layout; dev-artifacts contains everything Greg needs to debug.

### Stage 9 — 3D Viewer

**Engine:** new module `packages/preview-3d/src/v0.1-viewer/`. Three.js.

**Behavior:**
- Single HTML page rendering the `PatternGraph`'s panels in static placement around a simple body proxy (cylinder + shoulders + hip plane is sufficient).
- Turn (orbit) and pan controls. No zoom restrictions.
- Panels rendered as flat 2D meshes, oriented vertically, placed where they would assemble (front in front, back in back, side seams on the sides).
- Body proxy is a wireframe or muted-color reference, not a photorealistic avatar.
- Export button in the corner: when clicked, triggers PDF generation (Stage 8 output is referenced).
- No editing affordances. View only, plus export.
- [started 2026-05-04] Current implementation emits a Three.js static assembly preview sourced from PatternGraph scene data. It renders front/back panels around a muted body proxy and seam-pair guides, without cloth simulation.

**Output:** `garments/a-line-dress-tunic/outputs/v0.1-demo/viewer.html`.

**Done when:** the page loads, shows panels in plausible static placement, turn/pan works, export button produces the PDF.

**Important:** the page is **not** a "drape preview." It is a static panel layout. Label it accordingly: "3D layout preview" or "static assembly preview." See the drape vocabulary note in `docs/design/personas/persona-1-example-flows.md`.

### Stage 10 — Dev Instrumentation

**Behavior:**
- `readiness.json` (existing) — extended with: per-stage timing, per-landmark confidence, scale-calibration evidence, marker consumption metrics.
- New: `debug-overlay.html` — renders the input image with the system's labeled curves overlaid in colors keyed to landmark type, confidence shown as transparency or numeric label.
- New: `interpretation-trace.json` — per-curve scoring logs for the heuristic interpreter.
- [started 2026-05-04] Current implementation writes `debug-overlay.html` for sketch-driven runs. It overlays trace curves and exposes trace readiness, interpretation status, drafting state, scale evidence, landmark confidence, curve IDs, and assumptions. Score-table interpretation traces remain future work.

**Output:** `dev-artifacts/` directory with all of the above.

**Done when:** Greg can open `debug-overlay.html` and see exactly what the system labeled and how confident it was, for any input.

## UI Surface

**Total UI for v0.1:** one HTML page (`viewer.html`) per processed input.

The page contains:
- A header with the garment name and source input filename.
- The Three.js scene as the main viewport (most of the page).
- Turn/pan controls (mouse drag for orbit, modifier+drag for pan).
- An "Export PDF" button in the corner.
- A small (collapsible) "Assumptions" panel listing what the system assumed in design language.
- No upload UI in the page itself. Inputs are dropped into a directory or passed via CLI; the viewer is *output*, not a workflow.

**Files outside the page:**
- `package/` directory — the user-facing artifacts (PDF, cut sheet, assembly notes, marker layout).
- `dev-artifacts/` directory — engine instrumentation (readiness, debug overlay, interpretation trace, raw geometry).

The existing `app/dist/workbench.html` (variant comparison) is **renamed** to `app/dev-artifacts/dev-comparison.html` so its nature is honest.

## Output Package Format

```
garments/a-line-dress-tunic/outputs/<input-id>/
  package/
    pattern.pdf            # tiled letter/A4 with alignment marks, imperial
    pattern.svg            # source SVG (pattern panels)
    marker.svg             # 45" marker layout
    marker.pdf             # printable marker layout
    cut-sheet.md           # (or PDF) human-readable cut quantities and notes
    assembly.md            # (or PDF) construction order
    assumptions.md         # what the system guessed
    viewer.html            # Three.js viewer with export button
  dev-artifacts/
    readiness.json
    readiness.md
    debug-overlay.html
    interpretation-trace.json
    pattern-graph.json     # source PatternGraph
    vectorized.svg         # raw output of Stage 2
    scale-calibration.json
```

## Failure Mode

v0.1 has no user-facing failure surface. When the pipeline can't produce a confident pattern:

- **Soft failure (low-confidence interpretation, axis ambiguity, etc.):** pipeline proceeds with best-guess; assumptions surface in `assumptions.md`. User-facing artifact still exists.
- **Hard failure (input unreadable, all landmarks below 0.3 confidence floor, drafting math produces invalid geometry):** pipeline refuses. No user-facing artifact. `readiness.json` records why; Greg debugs from dev instrumentation.

The path from hard failure to retry is: Greg looks at `debug-overlay.html`, identifies what the system couldn't interpret, asks Kiko for a cleaner input or tweaks heuristic priors. No in-product retry loop.

## Acceptance Criteria

v0.1 is done when:

1. The pipeline runs end-to-end on at least one of Kiko's reference inputs without crashes.
2. The resulting `package/` directory contains a printable PDF, marker layout, cut sheet, assembly notes, assumptions document, and a working Three.js viewer.
3. The PDF prints at home (letter or A4), tiles correctly with alignment marks, and produces panels at the calibrated scale.
4. The 3D viewer shows the panels in plausible static placement with working turn/pan.
5. Greg can hold the printed pattern next to Kiko's reference and say "yes, this is the garment."
6. A sewing-literate review (Kiko herself, or another sewer) confirms the pattern is plausibly sewable into a muslin.

## Explicit Non-Goals

To prevent scope drift during implementation:

- We are not building a workbench, an editor, or a multi-pattern workspace.
- We are not building grading, variants, dependency propagation, or revision history.
- We are not building industrial export, marker optimization, or factory-facing tooling.
- We are not building cloth simulation, photoreal rendering, or fabric draping physics.
- We are not building manual landmark correction UI.
- We are not handling drape photos, noisy phone-photographed sketches, knit fabrics, or non-pullover closures.
- We are not handling garment families other than the A-line woven tunic.
- We are not building user accounts, sharing, IP/consent flows, or any kind of multi-user feature.

When tempted to add any of the above to "polish v0.1," remember: that work belongs in v0.5 (Persona 2) or v1+ (Persona 3). Park it cleanly.

- **Runtime:** Node.js for pipeline scripts; browser TypeScript for the viewer.

- **3D:** Three.js with OrbitControls.
- **PDF:** `pdf-lib` (MIT).
- **Validation:** existing `validation-core`.
- **Drafting:** existing `pattern-core` driven by the corpus JSON.

License flag: Potrace is GPLv2. Keep it as research/prior art unless we intentionally isolate it. The default Phase B runtime path is VTracer-backed and MIT via `@neplex/vectorizer`; browser runtime can later swap to `vtracer-wasm` behind the same bridge contract.

**Still open (workable around during implementation, will land as their phases hit):**

- **Croquis matching.** SSIM against a known croquis template is the cheapest figure-detection approach but may be brittle. If it fails on real inputs, fall back to manual scale specification in dev (set pixels-per-inch in a config file).
- **Marker layout for irregular hem sweep.** A simple strip-pack assumes rectangular bounding boxes; A-line panels with hem sweep may waste fabric. v0.1 accepts the waste; v1+ work optimizes.
- **Imperial / metric in the drafting corpus.** The FreeSewing factors are dimensionless ratios; ease values may be in cm. Codex must add explicit unit conversion at the corpus-consumption boundary.
- **Three.js body proxy.** Cylinder + shoulders + hip plane is sufficient for v0.1. If it looks too schematic, parametrize body proportions from the measurement set (which is now US Misses 8 by default).
- **Landmark vs measurement precedence.** Default for v0.1: **measurements scale, landmarks position.** The user's body measurements are the source of truth for size; landmarks tell the system *where* features go on that sized body. Refine during Phase E if it produces wrong-shaped patterns.
- **Hard-refuse confidence floor.** Each landmark slot has its own `ambiguity_threshold` (0.55–0.7) for soft-failure. Default global hard-refuse floor: **0.3**, applied per slot unless specific slots prove they need a different floor during Phase C.
- **Asymmetric input vs asymmetric garment.** Resolved 2026-05-04: split into a three-layer architecture — family-detection layer (hardcoded to A-line in v0.1; auto-detect is v0.5+; manual pre-select stays as a training-mode override), family-agnostic axis layer (Phase C ships symmetric / single-side-mirror / slight-asymmetry handling), family-specific feature layer (per-family priors declare any asymmetric features as new families are added). v0.1 handles symmetric inputs, single-side technical flats, and slightly-asymmetric drawing artifacts of A-line tunics; refuses inherently asymmetric *garments* (wrap dress, surplice, off-center detailing) at the family-lock level rather than the symmetry level. See decision-log entry 2026-05-04.
